# 1. Purpose

This document is the authoritative catalogue of transport-independent behavioural obligations derived from HJ-106 v2.2 Part A and normative API Contract obligations derived from its approved Part B for the Epic 1 `DetermineRequiredLicenceTypes`, `JoinCommunity`, `RegisterVendor` and `RetrieveRegisteredVendor` operations.

It defines what must be verified, why, at which boundary and with which prohibited outcomes. It contains no executable test code and does not prescribe frameworks, fixtures, mocks, brokers, databases or CI implementation.

# 3. Catalogue Conventions

| Convention | Definition |
|---|---|
| Test ID | Stable `VR-<AREA>-<NNN>` identifier. |
| Test Classification / Level | Each executable obligation uses exactly one HJ-006 classification and its mapped level: Domain / Unit, Application / Unit, Persistence Integration / Integration, Integration Contract / Integration or API Contract / API Integration. End-to-End is used only where a complete workflow cannot be verified lower. Contract Review / Non-executable is a review obligation. |
| Priority | Critical protects ownership, aggregate validity, idempotency, atomicity, event correctness or duplicate-effect prohibitions; Important protects required business behaviour, lifecycle, collaboration or failure behaviour; Standard covers supporting rules and optional boundaries; Proposed applies only to a technical convention whose authority remains unresolved. Blocked is not a Priority. |
| Automation | Automate, Parameterised automation, Contract automation after dependency, Manual contract review, or Deferred. |
| Dependency Status | Ready, Partially Blocked, Blocked, or Proposed pending approval. The approved Part B obligations in this catalogue are Ready. Deferred automation is used only when sequencing or approval prevents implementation; it is not a Priority. |
| Prohibited outcome | A mandatory negative assertion. Its omission makes the obligation incomplete. |
| Normative transport-independent test | Derived from HJ-106 Part A. |
| Normative API Contract test | Derived from approved HJ-106 Part B and kept distinct from transport-independent business behaviour. |
| Proposed test | Derived from a technical convention whose governing authority remains unresolved. |

Parameterized obligations may cover equivalent values or boundaries, but materially different outcomes have separate Test IDs.

HJ-107 owns the behavioural boundary established by HJ-106. HJ-013 owns complementary dependency enforcement, concrete mapping, transaction-mechanism, Transactional Outbox, relay-recovery and broker-mechanism verification. The same guarantee may have separate obligations at distinct boundaries, but identical obligations are not duplicated across the catalogues.

# 9. Completeness Analysis

- Every normative HJ-106 Part A operation, precondition, field category, invariant, outcome, event rule, failure, retrieval rule and scope exclusion maps to at least one Test ID in Section 8 for `DetermineRequiredLicenceTypes`, `JoinCommunity`, `RegisterVendor` and `RetrieveRegisteredVendor`.
- Requirements covered at multiple levels are intentionally split by observable boundary: for example, conditional creation rules at Domain level, persistence at Persistence Integration level and approved transport mapping at API Contract level.
- Domain/Integration Event separation, no Registration Session dependence, and the absence of prohibited business effects are repeated where distinct stimuli could regress independently.
- The complete Weekly Opening Hours schedule and daily states, fingerprint v2 and migrated legacy replay, corrected unreleased VendorRegistered v1 representation, retrieval fidelity and HTTP contract are explicitly covered alongside the existing Address, identity, concurrency, transaction, contact, publication and delivery obligations.
- Required Licence Types Determination is covered independently across validation, authoritative Address input, Compliance-owned deterministic policy, every applicability rule and boundary, the complete five-item result, transient review lifecycle, fresh pre-submission refresh, every controlled failure and universal no-side-effect behaviour.
- Direct RegisterVendor independence is explicit: no determination state, Rule Set Version, item, fingerprint or prerequisite enters registration, Vendor persistence, replay comparison, retrieval or events.
- Join Community is covered independently across the exact affirmative request, minimal Vendor verification, immutable first success, atomic persistence, equivalent replay, conflict, concurrency, every controlled failure, exact Integration Event, durable idempotent stub receipt, retention and all consent/delivery exclusions.
- Community separation is explicit: no Community value enters Vendor Registration or Vendor state; no Primary Contact enters Community; absence is not persisted as refusal; no communication is sent.
- Identity authentication, authorisation and caller association are scope exclusions, not blockers for the approved Epic 1 operations.
- The absence of a prescribed internal Domain Event payload and the absence of dedicated read-model infrastructure are deliberate non-requirements verified by Contract Review rather than executable schema tests.
- Approved Part B obligations are wholly separated in Section 6 and carry normal priority with Ready status; they are normative API Contract requirements, not transport-independent business rules.
- Potential overlap exists between failure rows and their triggering field/invariant rows; this is intentional because the former verifies orchestration and prohibited side effects while the latter verifies the lowest responsible rule boundary.
- HJ-107 owns behavioural and Integration Contract outcomes. Detailed browser presentation, concrete Compliance and Community stub wiring, dependency enforcement, persistence mappings and constraints, transaction failure injection, relay/broker mechanics and runtime verification remain complementary HJ-013 responsibilities; HJ-107 verifies approved observable boundaries without prescribing those mechanisms.
- No source ambiguity changes approved behaviour or the approved API Contract. The deliberate Identity exclusion is listed in Sections 7 and 10; no in-scope behavioural obligation remains blocked.
